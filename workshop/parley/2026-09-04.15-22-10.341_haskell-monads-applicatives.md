Your intuition is a useful special case, but it's worth loosening it up first, because it will otherwise make Applicative and transformers look arbitrary.

### Recalibrating the monad intuition

"Future computation not yet happened" describes `IO`, `State`, `Cont`, `Async` well. It [describes `Maybe`, `Either e`, `[]`, `Writer w` badly — in `Just 3` nothing is deferred; the value is right there.]

The framing that covers all of them: **`m a` is a value of type `a` sitting inside [some context**, and the monad interface tells you how to keep computing with that value *without ever leaving the context*.]

- `Maybe a` — an `a`, in the context of possible absence
- `Either e a` — an `a`, in the context of possible failure carrying `e`
- `[a]` — an `a`, in the context of nondeterminism (many candidates)
- `IO a` — an `a`, in the context of "obtainable only by performing effects"

What all of these share is the shape of the plumbing, not the temporal story. Deferral is one *kind* of context, not the essence.

### The ladder: Functor → Applicative → Monad

The three abstractions differ in exactly one dimension — **how much the later steps are allowed to depend on the earlier ones**. Look only at the types:

```haskell
fmap  :: Functor f     => (a -> b)   -> f a -> f b
(<*>) :: Applicative f => f (a -> b) -> f a -> f b
(>>=) :: Monad m       => m a -> (a -> m b) -> m b
```

- **Functor**: apply a pure function to the value inside. The context is untouched, and you can't add new context.
- **Applicative**: combine *several independent* contextual values. Note both `f (a -> b)` and `f a` already exist before you call `<*>` — the structure of the whole computation is fixed before anything runs.
- **Monad**: the second argument is `a -> m b`, a function that *manufactures* the context after inspecting the value. The rest of the computation can therefore depend on what came out of the previous step.

Concretely:

```haskell
-- Applicative: two effects, neither knows about the other
[(,) <$> Just 1 <*> Just 2        -- Just (1,2)]

-- Monad: the second effect is *chosen* based on the first value
Just 1 >>= \x -> if x > 0 then Just (x * 2) else Nothing
```

### Why bother with Applicative if Monad is strictly stronger?

Because the weaker interface buys you things the stronger one forbids. This is the part that usually clicks late, so it is worth being concrete.

**1. Static structure enables optimisation.** Since an applicative program's shape is known before execution, an interpreter can see all the effects up front and batch or parallelise them. This is exactly how Facebook's `Haxl` works: `<*>` on two data fetches issues them as one concurrent round-trip; `>>=` cannot, because the right-hand side does not exist until the left-hand side has produced a value.

**2. Semantics that violate the monad laws.** The canonical case is error accumulation:

```haskell
data Validation e a = Failure e | Success a

instance Semigroup e => Applicative (Validation e) where
  pure = Success
  Failure e1 <*> Failure e2 = Failure (e1 <> e2)   -- collect BOTH errors
  Failure e1 <*> _          = Failure e1
  _          <*> Failure e2 = Failure e2
  Success f  <*> Success a  = Success (f a)
```

`Validation` is deliberately **not** a Monad. It cannot be: `>>=` would have to short-circuit on the first failure (there is no `a` to feed the continuation), which contradicts accumulation. Form-validation reporting all three bad fields at once is an applicative-only capability.

**3. `traverse`.** Arguably Applicative's real payoff:

```haskell
traverse :: (Traversable t, Applicative f) => (a -> f b) -> t a -> f (t b)

traverse validateAge [12, 45, -3]   -- one effectful pass over a container
```

This needs only Applicative, so it works for parallel and accumulating effects too.

So: **use the weakest abstraction that does the job.** It maximises what both the compiler and the interpreter know about your program.

### Monad transformers: what problem they solve

Functors and Applicatives compose for free — `Compose f g` is always a Functor if `f` and `g` are, and likewise for Applicative. **Monads do not.**

Try to write `join` for a composed monad:

```haskell
join :: m (n (m (n a))) -> m (n a)
```

You are stuck at the inner `n (m ...)`: you need to swap `n` and `m`, and nothing in the `Monad` interface lets you commute two arbitrary monads. Hence you cannot mechanically stack `State` on top of `IO`.

The workaround is to write, by hand, a version of each monad that is **parameterised over an arbitrary base monad**:

```haskell
newtype StateT  s m a = StateT  { runStateT  :: s -> m (a, s) }
newtype ExceptT e m a = ExceptT { runExceptT :: m (Either e a) }
newtype ReaderT r m a = ReaderT { runReaderT :: r -> m a }
```

Note where `m` is threaded — that's the whole trick. `State s` is recovered as `StateT s Identity`. `lift :: (MonadTrans t, Monad m) => m a -> t m a` injects a base-monad action into the stack.

```haskell
type App = StateT Int (ExceptT String IO)

tick :: App ()
tick = do
  n <- get
  when (n > 10) $ lift (throwError "too big")
  liftIO (putStrLn ("n = " ++ show n))
  put (n + 1)
```

### The consequence people underestimate: order matters

Stacking is not commutative, and the difference is semantic, not cosmetic. Unfold the types:

```haskell
StateT s (Either e) a   ≅  s -> Either e (a, s)   -- error destroys the state
ExceptT e (State s) a   ≅  s -> (Either e a, s)   -- state survives the error
```

In the first, a failure gives you `Left e` and the state is gone. In the second, you always get a final state *plus* a success-or-failure. Which one you want depends on whether you're modelling a transaction rollback or an audit log. Choosing a stack is a design decision about effect interaction.

### Known costs of transformers

Being critical, since this is where the abstraction shows its age:

- **Quadratic instances.** Every transformer needs a `MonadState`/`MonadReader`/... instance for every *other* class in the stack. `mtl` exists precisely to hide `lift` behind those classes, and it's an O(n²) maintenance burden.
- **No two of the same layer.** Two `StateT`s in one stack are ambiguous under `mtl`'s classes; you need explicit `lift`s or newtype wrappers.
- **Performance.** Deep stacks build closures per bind; GHC's inliner sometimes collapses them and sometimes does not, so the cost is hard to predict.

This is why a lot of production Haskell converged on the **`ReaderT` over `IO` pattern** — one layer, mutable references for state, exceptions for errors — and why algebraic-effect libraries (`polysemy`, `effectful`, `fused-effects`) exist as alternatives.

Good — you've spotted a real confusion, and it's one of Haskell's genuine teaching failures. Three different things get talked about as "m".

### Three distinct entities

```haskell
data Maybe a = Nothing | Just a
```

This one line declares:

| Name | Kind of thing | Lives at | Type/kind |
|---|---|---|---|
| `Maybe` | **type** constructor | type level | `Maybe :: * -> *` |
| `Just` | **data** constructor | value level | `Just :: a -> Maybe a` |
| `Nothing` | data constructor | value level | `Nothing :: Maybe a` |
| `Monad` | **typeclass** | constraint level | `Monad :: (* -> *) -> Constraint` |

Your instinct "m is essentially a function" is **correct**, but it's a function on *types*: `Maybe` takes a type and gives back a type. `Just` is the separate, value-level function that takes an `a` and builds the actual runtime value. They're deliberately given the same-ish role in your head, but they live in different namespaces (which is why `data Maybe a = Just a` can legally reuse a name — `data Pair a = Pair a a` is idiomatic and the two `Pair`s are unrelated identifiers).

`Monad` is not in that family at all. It's a *class* — a set of (type constructor, implementation) pairs.

### Why sometimes `m a` and sometimes bare `m`

This is your real question, and the answer is **kinds** — types of types.

[```haskell
Int          :: *          -- a complete type; values exist
Maybe        :: * -> *     -- incomplete; needs one type] argument
Maybe Int    :: *          -- complete
Either       :: * -> * -> *
Either String :: * -> *    -- partially applied!
```


Now look at the two class declarations side by side:

```haskell
class Eq a where            -- a :: *
  (==) :: a -> a -> Bool

class Monad m where         -- m :: * -> *
  (>>=) :: m a -> (a -> m b) -> m b
```

`Eq` classifies *complete* types, so you write `instance Eq Int`. `Monad` classifies *incomplete* ones, so you write `instance Monad Maybe` — never `instance Monad (Maybe a)`.

**Why it must be that way:** look at `>>=`. It mentions `m a` *and* `m b`. The class needs to hold the container fixed while varying the payload. If the class were parameterised over the whole applied type `Maybe Int`, there'd be no way to name `Maybe Bool` as "the same context with a different payload." So `m` must stay unapplied in the class head, and gets applied inside the method signatures.

That's the rule: **bare `m` where you're naming the context itself; `m a` where you're naming a value.**

Currying works at the type level too, which is how `Either` gets an instance:

```haskell
instance Monad (Either e) where ...   -- Either e :: * -> *, error type fixed
```

The error type `e` is baked in; only the success type varies. Same reason `StateT s m` — you saw `[newtype StateT s m a]` earlier, and `Monad (StateT s m)` applies it to all but the last argument. 

### On "the context can be empty"

Right, and it has a name:

```haskell
[newtype Identity a = Identity { runIdentity :: a }]
```

Zero extra information — purely a marker so that instance resolution has something to dispatch on. That's exactly why `type State s = StateT s Identity` works: you need *a* monad in the base position, so you supply the one that does nothing.

But be careful with "marker interface": a Java marker interface (`Serializable`) is empty. A Haskell typeclass carries **implementations**, and GHC compiles a constraint like `Monad m =>` into an extra hidden argument — a record of function pointers (a *dictionary*). So `Monad` is closer to an interface with methods, resolved statically by type rather than dynamically by the receiver. There is no value at runtime that "knows" it's a monad; the call site knows.

### Decoding `(,) <$> Just 1 <*> Just 2`

First, `(,)` is the pair **data constructor** used prefix, and like all data constructors it's an ordinary curried function:

```haskell
(,) :: a -> b -> (a, b)
(,) 1 2  ==  (1, 2)
```

The three operators:

```haskell
($)   ::                  (a -> b) ->   a ->   b   [-- plain application
(<$>) :: Functor f     => (a -> b) -> f a -> f b   -- = fmap]
(<*>) :: Applicative f => f (a -> b) -> f a -> f b
```

Read the angle brackets as "this side is wrapped in a context." `$` has nothing wrapped; `<$>` has the argument wrapped; `<*>` has *both* the function and the argument wrapped.

Your algebra observation is half right, and the correction is useful.

The *core* set is small and stable: `Monoid`, `Functor`, `Applicative`, `Monad`, `Traversable`, `Alternative`. That's about it, and it hasn't really changed in 20 years. ### `newtype`

```haskell
newtype Identity a = Identity a          -- legal: 1 constructor, 1 field
data    Maybe    a = Nothing | Just a    -- 2 constructors → must be `data`
```

`newtype` is `data` restricted to **exactly one constructor with exactly one field**. In exchange for that restriction, GHC **erases it at compile time**: `Identity Int` and `Int` have identical runtime representation, and `Identity`/`runIdentity` compile to nothing. `data` would allocate a real box.

The purpose is not wrapping data. It is **creating a distinct type identity so you can attach a different instance**:

[```haskell
newtype Sum     = Sum     { getSum     :: Int }]
newtype Product = Product { getProduct :: Int }

instance Monoid Sum     where mempty = Sum 0;     Sum a     <> Sum b     = Sum (a+b)
instance Monoid Product where mempty = Product 1; Product a <> Product b = Product (a*b)
```

`Int` has two equally good monoids. Haskell allows only one instance per (class, type) pair, so you [mint two types that are `Int` at runtime and different at compile time. **This is the whole reason `newtype` exists.**]

### The record syntax

```haskell
newtype Identity a = Identity { runIdentity :: a }
```

is *exactly* equivalent to:

```haskell
newtype Identity a = Identity a
runIdentity :: Identity a -> a          -- auto-generated by the braces
runIdentity (Identity x) = x
```

The braces name the field, and naming a field gives you the **accessor function for free**. That's all. The `runX` convention exists because the accessor reads as a verb at the call site.

Now `StateT`:

```haskell
newtype StateT s m a = StateT { runStateT :: s -> m (a, s) }
```

The thing being wrapped is a **function**, `s -> m (a, s)`: give it a starting state, get back (in monad `m`) a result paired with the new state. The generated accessor is:

```haskell
runStateT :: StateT s m a -> s -> m (a, s)
```

so `runStateT action 0` is "run this stateful action starting from 0."

**Why wrap a function in a newtype at all?** Precisely because of the kind rule from your last message. You cannot write `instance Monad (s -> m (a, s))` — that isn't a type constructor of kind `* -> *`, and functions already have a `Monad` instance anyway. The newtype manufactures a name you can hang the instance on:

```haskell
StateT       :: * -> (* -> *) -> * -> *
StateT s m   :: * -> *                    -- ✔ correct kind
instance Monad m => Monad (StateT s m)
```

### Reading `f a` — is it symbol manipulation?

**For type-checking: yes, purely.** `f a` is type-level function application, identical in mechanics to value-level juxtaposition. The compiler unifies symbols; it doesn't "understand" anything.

**For knowing what the code does: no** — you need the instance. The signature tells you what's *possible*; the instance tells you what *happens*.

But here's the leverage, and it's the thing worth internalising: because `a` and `b` in `fmap :: (a -> b) -> f a -> f b` are **universally quantified**, `fmap` cannot inspect them. It cannot compare, print, or branch on an `a`. It can only *route* them. This is **parametricity**, and it means the signature alone eliminates almost every possible implementation. You often genuinely can read the type and know the function.

### `{}` — yes, it's the field, but the payoff is a function

```haskell
newtype Sum = Sum Int                      -- no name for the field
newtype Sum = Sum { getSum :: Int }        -- field named `getSum`
```

Both define the same type with the same runtime representation. The braces add exactly one thing: GHC writes this function for you.

```haskell
getSum :: Sum -> Int
getSum (Sum n) = n
```

That's the entire difference. Without the braces you'd unwrap by pattern matching, `case s of Sum n -> n`. With them you just write `getSum s`. (For `data` types with several fields you also get record-update syntax, `p { age = 31 }`, but for a one-field newtype that's irrelevant.)

### Why `newtype Sum = Int` is illegal

Because the two sides of `=` live in **different namespaces**, and you've written a type on the right-hand side where a *value-level constructor* is required.

```haskell
newtype Sum = Sum Int
--         ↑     ↑    ↑
--    type name  |    field type (type namespace)
--               data constructor name (value namespace)
```

The right-hand side is the recipe for **building and taking apart values at runtime**. You need a tag to write `Sum 3` and to pattern-match `Sum n <- x`. `Int` alone gives you no such handle.

Amusingly, `newtype Sum = Int` does parse — GHC reads the uppercase `Int` as *defining a nullary data constructor* that happens to be spelled `Int` (harmless, since types and values are separate namespaces). It then rejects it with roughly *"a newtype constructor must have exactly one field"*, because you declared zero.

### The thing you were actually reaching for is `type`

```haskell
type    Sum = Int        -- synonym:   Sum IS Int, everywhere, always
newtype Sum = Sum Int    -- new type:  distinct at compile time, free at runtime
data    Sum = Sum Int    -- new type:  distinct, and boxed at runtime
```

| | distinct type? | runtime cost | can carry its own instance? |
|---|---|---|---|
| `type` | no — pure alias | none | **no** |
| `newtype` | yes | none | yes |
| `data` | yes | allocation | yes |

`type Sum = Int` is legal and compiles, but it's just an abbreviation — `Sum` and `Int` are literally interchangeable, so `instance Monoid Sum` *is* `instance Monoid Int`. That defeats the purpose. `newtype` is the construct that gives you a genuinely new type at zero runtime cost, which is why it exists.

### Is `getSum` significant?

No. It's an arbitrary identifier you chose; `unSum`, `toInt`, `xyzzy` all work identically. Two soft constraints:

- It becomes a top-level function, so it must not clash with another name in the module.
- Convention is `getX` or `unX` or `runX`. `run` signals "this wrapper holds a function or an action" — hence `runStateT`, `runIdentity`; `get`/`un` signal "this just holds a value" — hence `getSum`.

Only convention. Nothing in the compiler cares.

One correction to my earlier sketch: the real one in `base` is polymorphic, `newtype Sum a = Sum { getSum :: a }`, so it works for any `Num a`. I fixed it to `Int` to keep the monoid instances readable.

```haskell
-- try it
import Data.Monoid
main = do
  print (getSum     (foldMap Sum     [1..10]))   -- 55
  print (getProduct (foldMap Product [1..5]))    -- 120
```

Same list, same fold, different monoid — selected purely by which newtype you wrap with. That's the mechanism paying for itself.
