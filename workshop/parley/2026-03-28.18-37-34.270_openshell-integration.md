Good timing on this question — OpenShell shipped recently and is explicitly alpha, so the answer is partly "yes, that's it" and partly "the file-sharing piece is the weak spot right now."

### What OpenShell actually is

Your mental model is right but slightly undersells it. It is not "a nicer Docker container" — the distinguishing claim is that enforcement is out-of-process: when agent code opens an outbound connection, a proxy inside the sandbox intercepts it. That matters for exactly the reason you care about: a guardrail living inside the agent's own process is still part of the thing you're constraining.

The pieces: Gateway (control plane, lifecycle + auth boundary), Sandbox (the isolated runtime), Policy Engine (filesystem/network/process constraints), and a Privacy Router that controls where inference traffic goes. Underneath it's Landlock LSM, seccomp syscall filtering, default-deny networking, and unprivileged process identity — standard Linux kernel mechanisms, not proprietary NVIDIA components.

### Is "start sandbox, then clone inside" it?

Essentially yes — that is the documented pattern. The trailing command is the sandbox's canonical main process; OpenShell starts it once and attaches your terminal, and the base image already ships claude, opencode, codex, copilot.

Two things you're likely underestimating:

**1. Credential injection is already half of your "unified proxy" idea.** OpenShell manages credentials as *providers* — named bundles injected at sandbox creation. The CLI auto-discovers credentials for recognized agents from your shell environment. Credentials never land in the sandbox filesystem; they're injected as environment variables at runtime. So the agent's API key is scoped to the destinations the provider's policy authorizes.

**2. The network policy granularity is finer than "allow/deny host."** The canonical tutorial example: the default `github_rest_api` policy allows GET but blocks PUT/write to GitHub — a sandbox-level restriction, not a token issue, so no token will make pushes work until the policy is updated. Also note GraphQL is blocked in sandboxes, so GitHub CLI usage is REST-only.

The workflow loop NVIDIA intends is itself agentic: you ask the agent to read the sandbox logs for denied requests, and it diagnoses the root cause; the enforcement engine can reason about the roadblock and propose a policy update for your approval. That's much closer to your RL-gym framing than a static Dockerfile.

**On your unified proxy:** I'd push back on building it separately. OpenShell *is* a TLS-terminating egress proxy with declarative per-endpoint rules, plus `inference.local` routing to local backends like Ollama or vLLM, with the gateway injecting credentials so agents never receive the real keys. Your semantic filter probably belongs as a custom endpoint policy or a local inference route behind that router, not as a second hop you maintain.

### The file-access question — this is the honest gap

There is **no first-class live bidirectional host mount**. From the open feature request: OpenShell sandboxes currently have no mechanism for live bidirectional access to host directories; file transfer is limited to one-time `--upload` / `sandbox upload` tar-over-SSH copies. A `--mount host:container:mode` flag is [requested but not shipped](https://github.com/NVIDIA/OpenShell/issues/500).

Your four realistic options, worst to best for your case:

**a) Docker/Podman bind mount (exists, but read the warning).** Bind mounts share gateway-host filesystem resources with the sandbox. The docs say they may be considered insecure because they can negate OpenShell controls such as workspace isolation and filesystem policy — use only after enabling them in the Docker driver table. Note "**gateway-host**": on a Mac your gateway host is a Linux VM, so the sharing chain is Mac → VM → container. I'm moderately confident this works but expect friction; I don't know the current macOS qualification status.

**b) SSH as the channel.** The CLI exposes `sandbox ssh-config`, `upload`, `download`, `connect`, and `--editor` launches VS Code or Cursor into the sandbox workspace, installing an OpenShell-managed SSH include file rather than editing your main `~/.ssh/config`. Since you're a Neovim/Parley user, that same SSH host entry gives you `sshfs`, `scp://` in Neovim, or just running Neovim inside the sandbox over `connect`.

**c) Upload at creation, git as the return path.** Note uploads inside a Git repo respect `.gitignore` by default, so `node_modules`, build artifacts and caches aren't transferred — that's the "20-minute hang" trap someone else already hit.

**d) Clone inside, push out.** This is what I'd actually recommend, and it's not a workaround — it's consistent with your own premise.

### The part worth arguing about

You framed the human role as "set up the gym, let the agent run wild." If you then mount your live checkout read-write into the sandbox, you've reintroduced the shared-state coupling the sandbox existed to remove, and you get the worst of both: isolation theater plus a filesystem you and the agent race on. The gym analogy cuts the other way — a gym has an **episode boundary**. Let the sandbox be ephemeral, let the agent clone fresh, and make **git branches the only egress channel for work product**. You review diffs on the Mac with your normal tools; the agent never touches your working tree.

The corollary you'll hit next: a gym also needs a **reward signal**. Sandboxing gives you reset and blast-radius control, but the thing that actually lets an agent "run wild" productively is a fast, trustworthy verifier inside the box — tests, typecheck, lint, all runnable offline with a `default-deny` network. If your repo can't be validated without network access, the sandbox will mostly generate policy-denial noise. I'd invest there before the semantic proxy.

One caveat on all of this: it's self-described alpha, "single-player mode" — one developer, one environment, one gateway, expect rough edges.

Short answer: **No**, `--editor` currently only supports `vscode` and `cursor`. But you don't really need it — the `--editor` flag is just a convenience wrapper that generates SSH config and launches the editor's Remote-SSH integration. For nvim, you have better options anyway.

### What `--editor` actually does

The `--editor` flag opens the sandbox in VS Code or Cursor — it generates a temporary SSH config entry and invokes the editor's Remote-SSH mechanism. When `--editor` is used, OpenShell keeps the sandbox alive and installs an OpenShell-managed SSH include file instead of cluttering your main `~/.ssh/config`.

That's it. It's a thin shim. For nvim, you can do the same thing manually in ~10 seconds.

### What to do instead

**Option 1: SSH in and run nvim inside the sandbox** (simplest)

```bash
# Create sandbox, keep it alive
openshell sandbox create --name my-sandbox --sync

# Get SSH config
openshell sandbox ssh-config my-sandbox >> ~/.ssh/config
# or just connect directly:
openshell sandbox connect my-sandbox

# Inside the sandbox, run nvim
nvim .
```

The sandbox base image is a full Linux environment. You can install nvim inside it, or better — build a custom sandbox image (`--from ./my-sandbox-dir`) with your nvim config baked in.

**Option 2: SSHFS mount + local nvim** (edit locally, files live in sandbox)

```bash
# Get the SSH host name
openshell sandbox ssh-config my-sandbox
# Mount the sandbox filesystem locally
mkdir -p ~/mnt/sandbox
sshfs openshell-my-sandbox:/sandbox ~/mnt/sandbox

# Now use local nvim
nvim ~/mnt/sandbox/
```

**Option 3: [remote-sshfs.nvim](https://github.com/nosduco/remote-sshfs.nvim)** (nvim-native)

remote-sshfs.nvim allows you to edit files on remote hosts via SSHFS as if they were local, loosely based on the VSCode Remote-SSH extension. Point it at the OpenShell SSH host and you get telescope integration, live grep, etc — all running over SSH to the sandbox.

**Option 4: tmux inside sandbox** (most ergonomic for nvim users)

```bash
openshell sandbox connect my-sandbox
# Inside:
tmux new -s dev
nvim .
```

This is probably the most natural fit. You get session persistence, and if you disconnect, your nvim session survives inside tmux in the sandbox.

### Custom sandbox image with your nvim config

Create a directory like `./my-sandbox/` with a `Dockerfile` and `policy.yaml`:

```dockerfile
FROM ghcr.io/nvidia/openshell-community/base:latest

RUN apt-get update && apt-get install -y neovim tmux ripgrep fd-find

# Copy your nvim config
COPY nvim/ /home/sandbox/.config/nvim/
```

Then:
```bash
openshell sandbox create --from ./my-sandbox --sync -- bash
```

This way every sandbox you spin up has your nvim config ready to go.

### Bottom line

The `--editor` flag is a VS Code / Cursor convenience. As an nvim user, you're actually in a *better* position — nvim-over-SSH is a first-class workflow, not a bolted-on extension. The SSH config that OpenShell generates is all you need.

### Dotfiles: Mac vs Linux isn't that bad

Most of what matters for an agentic coding sandbox is cross-platform already:

- **nvim config** — pure Lua/vimscript, works identically on Linux
- **tmux.conf** — identical
- **shell aliases / .zshrc / .bashrc** — 95% portable
- **ripgrep, fd, fzf configs** — identical

The only Mac-specific bits are usually GUI tools (Hammerspoon, Raycast, etc.) and `brew`-isms — none of which matter inside a sandbox. You likely just need to copy your `~/.config/nvim/` and `~/.tmux.conf` into the image and it works.

### Repo structure

```
my-project/
├── .openshell/
│   ├── Dockerfile
│   ├── policy.yaml
│   └── dotfiles/
│       ├── nvim/          # symlink or copy of your ~/.config/nvim
│       ├── tmux.conf
│       └── bashrc
├── bootstrap.sh           # the "one command"
├── src/
└── ...
```

### Dockerfile

```dockerfile
FROM ghcr.io/nvidia/openshell-community/base:latest

# System deps
RUN apt-get update && apt-get install -y \
    neovim \
    tmux \
    ripgrep \
    fd-find \
    git \
    curl \
    unzip \
    build-essential \
    python3 python3-pip \
    nodejs npm \
    && rm -rf /var/lib/apt/lists/*

# Dotfiles
COPY dotfiles/nvim/ /home/sandbox/.config/nvim/
COPY dotfiles/tmux.conf /home/sandbox/.tmux.conf
COPY dotfiles/bashrc /home/sandbox/.bashrc

# Fix ownership
RUN chown -R sandbox:sandbox /home/sandbox/
```

### policy.yaml

```yaml
version: "1.0"

filesystem:
  writable:
    - /sandbox
    - /tmp
  readable:
    - /usr
    - /etc
    - /home/sandbox

network:
  egress:
    allow:
      - "github.com:443"
      - "registry.npmjs.org:443"
      - "pypi.org:443"
      # add your package registries
    deny:
      - "*"  # deny everything else by default
```

### bootstrap.sh

```bash
#!/usr/bin/env bash
set -euo pipefail

SANDBOX_NAME="${1:-$(basename $(pwd))}"

echo "Building sandbox image..."
openshell sandbox create \
    --name "$SANDBOX_NAME" \
    --from .openshell \
    --sync \
    -- bash

echo "Sandbox '$SANDBOX_NAME' ready."
echo "Connect with: openshell sandbox connect $SANDBOX_NAME"
```

Then the workflow is:

```bash
git clone git@github.com:you/my-project.git
cd my-project
./bootstrap.sh
# done — connect and go
openshell sandbox connect my-project
```

### One subtlety: nvim plugin installation

Your nvim config probably uses lazy.nvim or similar, which pulls plugins on first launch. Two options:

1. **Lazy approach** — just let it happen on first `nvim` invocation inside the sandbox. Requires github.com in your network allow list (which you'd want anyway).
2. **Hermetic approach** — add a `RUN` step in the Dockerfile that runs nvim headless to install plugins at image build time:

```dockerfile
# After copying nvim config
RUN su sandbox -c 'nvim --headless "+Lazy! sync" +qa 2>/dev/null || true'
```

Option 1 is fine for personal use. Option 2 is better if you want truly reproducible environments or if multiple people share the repo.

### Per-project customization

The beauty of checking `.openshell/` into each repo is that different projects can have different policies and different toolchains. A Rust project gets `rustup` in the Dockerfile; a Python ML project gets `conda`; the network policy for one might allow `huggingface.co`, another might not. The sandbox definition *is* part of the project, same as `.devcontainer/` or `docker-compose.yml`.

So yes — this is exactly the right pattern. One directory, one bootstrap command, hermetic and version-controlled.
