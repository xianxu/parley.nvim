    5  # Parley.nvim
    6  
    7  <!-- panvimdoc-ignore-end -->
    8  
    9  Parley started as a Neovim chat notebook for LLM conversations. It's created to help me research on a topic with the help with many different agents. A side goal of Parley is really a test bed for me to play with agentic coding workflow. This leading me to see a future of **markdown as state, nvim/`coding agent` as human operator interface, the beginning of future operating system for startups**. 
   10  
   11  There are just many different ways user can leverage it. With Parley, you have all the power of Neovim at your fingertips in your LLM chat, thus making comprehensive research easier. All your chat history also lives in plain markdown files, you can easily search through using local tools. You can even direct your coding agent to act according to the "brainstorming" chat thread you had with other agents, for example. The possibilities seem endless.
   12  
   13  Compared to stock chatbot, Parley supports a "tree of chats", essentially allowing user to branch of some side topic, in a linked but different file. This way, information is always organized, matching how human research and learn a topic.
   14  
   15  The philosophy behind Parley is Keep Things Simple, and Local, and a bit of Unix:
   16  - Keep chats as plain Markdown files you can edit any place
   17  - The chat transcript file has the full state of LLM chat
   18  - Highly configurable but also have good default out-of-box
   19  - Keep the workflow keyboard-first and fast
   20  - Keep behavior predictable across different chat providers
   21  - Leverage Neovim, and all its goodies
   22  - Minimal dependencies, install and it works, all you need is your API keys
   23  
   24  ## Developer performance testing
   25  
   26  Run `make perf` to collect Parley's report-only chat-typing benchmark. See
   27  [TOOLING.md](TOOLING.md#chat-typing-performance-report) for the scenario, output schema,
   28  structural correctness gates, and optional MarkdownPreview comparison.
   29  
   30  Despite of such simple interface, it's very powerful, sometimes more so than official app
   31  - You can use "any" LLM providers, mix in the same conversation input from many different LLMs
   32  - Your chat transcript can be as complex as a tree with branches, to allow you to explore into different directions, without being forced into a linear conversation
   33  - You can jump easily between such tree branches
   34  - You can access your private local file, and private Google Drive file through oauth
   35  - You can edit anything in the transcript, including LLM responses, which presumably would influence the agent's future responses, a soft prompt engineering. You are constructing an understanding of a topic together with the help of LLMs
   36  - All you chat history in one place locally, you can search and further refine with whatever tools you want
   37  - Tweak system prompts to best suit your needs
   38  - Have many different chat threads active in different vim buffers, terminals etc., no limits
   39  - Easily switch between different chat threads, instant search experience with Chat Finder <C-g>f anywhere in Neovim
   40  - Also a good learning tool for LLM interactions, e.g. in raw request/response modes, you see all request/response details
   41  - New LLMs support web search and grounding, you can easily enable or disable if you want it to be faster
   42  - Publish your chat as markdown or HTML, for blogging or sharing, e.g. [a chat about async programming](https://xianxu.github.io/2025/05/12/conversation_around_concurrent_programming_models.html)
   43  - Share your brainstorming transcripts with your coding agents to start materializing it!

   48  - [`lualine.nvim`](https://github.com/nvim-lualine/lualine.nvim) for status line integration. Not missing much if not available.

   50  - [`pandoc`](https://pandoc.org/) for exporting non-chat markdown files to HTML (`<C-g>eh`). Install with `brew install pandoc`.

   64                  -- googleai = ...
   65                  -- ollama = ...
   66              },
   67          })

   69  }

  104  ## First 60 Seconds
  105  
  106  1. Run `:ParleyChatNew` (default shortcut: `<C-g>c`) to create a new chat.
  107  2. Type your question after `💬:`, no need for anything else. `Topic: ?` will be automatically filled with summary of your question.
  108  3. Run `:ParleyChatRespond` (default shortcut: `<C-g><C-g>`) with mouse on the question line.
  109  4. Get a response from the agent after `🤖:`, streaming in real time. A slow
  110     start shows a playful virtual progress line after one second; it never enters
  111     the Markdown transcript.
  112  
  113  A Parley chat is a normal markdown file with a header and alternating `💬:` / `🤖:` blocks.

  115  ## Basic Commands
  116  
  117  Most-used defaults:
  118  
  119  **Global**
  120  - `<C-g>c` new chat - global hotkey
  121  - `<C-g>f` find chat - opens immediately with a cancellable animated
  122    `scanning…` row while Chat Finder asynchronously discovers chat headers; an
  123    exact background prewarm is reused when available
  124  - `<C-n>f` find notes - the same immediate loading experience over recursive
  125    note metadata; note bodies are not read, and special folders still bypass
  126    recency filtering
  127  - `<C-y>f` find issues - asynchronously read issue/history metadata with
  128    vocabulary-backed ordering and repository facets in super-repo mode
  129  - `<C-j>f` find vision initiatives - asynchronously read YAML file bundles,
  130    preserving file/parser order and exact source-line jumps
  131  - `<C-g>m` find Markdown files - directory facets in ordinary repo mode and
  132    repository facets in super-repo mode; query text and facet choices persist
  133    across finder reopenings within the current Neovim session. When a facet bar
  134    wraps beyond its visible height, point at the bar and use the mouse wheel to
  135    reach the remaining facets. The picker opens immediately with a cancellable
  136    animated `scanning…` row while Git discovers all tracked Markdown files plus
  137    untracked, non-ignored Markdown files; ignored untracked files and Markdown
  138    inside nested repositories or submodules are excluded from the parent scan.
  139  - `<C-g>p` toggle peer (super-repo) mode - aggregate reads across sibling
  140    `.parley` repositories. The explicit repo/peer choice persists separately for
  141    each repository; an unsaved repository starts in ordinary repo mode.
  142  
  143  **In Chat Buffer**
  144  - `<C-g>?` show key bindings
  145  - `<C-g><C-g>` respond
  146  - `<M-CR>` respond (normal/insert); **visual-select a phrase + `<M-CR>`** → inline term definition — immediately shows a spinner after the selection, then on success replaces it with a markdown footnote reference/footer and centered diagnostic float, honoring `:ToggleWebSearch` for unfamiliar terms
  147    - Reopened chats recover multi-word highlights from structured footnotes such as `[^acos]: "Advertising Cost of Sales". Ratio...`; generated ids such as `[^serverless-functions]` also recover `serverless functions` from the slug when that phrase appears before the reference.
  148  - `<C-g>G` respond all
  149  - `<C-g>x` stop
  150  - `u` / `<C-r>` undo/redo normally; while a response is pending, Parley asks
  151    before cancelling that buffer's request and changing history (default: No)
  152  - `<C-g>t` chat outline
  153  - `<C-g>a` change agent
  154  - `<C-g>P` next system prompt
  155  - `<C-g>s` skill picker (review, voice-apply, etc.)
  156  - `<C-g>b` branch/prune - move the current exchange and following exchanges to
  157    a child chat
  158  
  159  Tool-fold toggling is configurable but unbound by default. To opt in, set
  160  `chat_shortcut_toggle_tool_folds = { modes = { "n" }, shortcut = "<leader>tf" }`.
  161  - `<C-g>l` toggle follow cursor
  162  - `<C-g>i` to insert a fork in the chat tree, can be inline or standalone
  163  - `gf` smart go-to-file: on an ariadne artifact ref (`ariadne#11`, `#15 M4`, `pair#84`) resolves it and jumps (family picker when it resolves to many); on a plain path, Vim's native `gf`
  164  
  165  **Corresponding commands**
  166  - `:ParleyChatNew` create a new chat
  167  - `:ParleyChatFinder` asynchronous chat finder with joinable metadata prewarm
  168  - `:ParleyNoteFinder` asynchronous recursive note finder with joinable metadata prewarm
  169  - `:ParleyIssueFinder` asynchronous issue/history finder
  170  - `:ParleyVisionShow` asynchronous project-initiative finder
  171  - `:ParleyMarkdownFinder` asynchronous Git-aware Markdown finder with contextual directory/repository facets
  172  - `:ParleyChatRespond` answer current question
  173  - `:ParleyChatRespondAll` regenerate from start to cursor
  174  - `:ParleyStop` stop running generation
  175  - `:ParleyOutline` display questions in this buffer for navigation
  176  - `:ParleyKeyBindings` show active Parley keyboard shortcuts
  177  - `:ParleyAgent` switch agent
  178  - `:ParleySystemPrompt` switch system prompt
  179  - `:ParleyToggleFollowCursor` toggle live cursor-follow during streaming
  180  
  181  All five disk-backed finders open their picker shell immediately and keep the
  182  prompt live while `scanning…` animates. Settled results replace the loading row
  183  in one update; partial failures retain usable rows with a warning, total failure
  184  leaves a nonselectable error, and Esc cancels picker-owned work. Markdown uses
  185  Git's tracked union untracked-nonignored boundary, so ignored vendor trees are
  186  not searched in either ordinary or super-repo mode.

  188  ## What Parley Supports
  189  
  190  - Providers: OpenAI, Anthropic, Google AI, Ollama, OpenAI-compatible endpoints, and CLIProxyAPI.
  191    - parley can **manage a local `cliproxyapi`** for you — it renders the config from Lua and lazily starts/reuses/health-checks the proxy. `:ParleyProxy status|start|stop|restart|models <provider>|providers|login <provider>|reap|update` (bare `:ParleyProxy` prints per-subcommand help). **On by default but dormant** — only acts when a cliproxyapi-provider agent runs, and reuses an existing proxy if one is up; a fresh machine needs `brew install cliproxyapi` + a one-time `:ParleyProxy login`. Set `cliproxy = { manage = false }` to opt out. See [atlas/providers/cliproxy-managed.md](atlas/providers/cliproxy-managed.md).
  192  - File context with `@@path/to/file` and directory patterns.
  193  - Web search toggle for supported providers, with semantic search/reasoning status shown in the response's transient virtual progress line.
  194  - Outline navigation, highlighting.
  195  - Export chat to markdown or HTML, for blogging, e.g. [a chat about async programming](https://xianxu.github.io/2025/05/12/conversation_around_concurrent_programming_models.html).
  196  - Misc: notes, interview mode, raw mode, and export.

  198  ## Configuration Entry Points
  199  
  200  Common options live in `setup()`:
  201  - `api_keys`
  202  - `chat_dir`
  203  - `notes_dir`
  204  
  205  Merge behavior in `setup(opts)`:
  206  - `agents`, `system_prompts`, and `hooks` are merged by key/name, so you can override only selected entries.
  207  - Most other top-level keys are replaced when provided (for example `chat_dir`, `chat_dirs`, `notes_dir`, `chat_template`, `raw_mode`, `highlight`, `chat_memory`, `providers`, `api_keys`).
  208  - Practical rule: for non-merged tables, provide the full table you want, not just one nested field.
  209  - Reference [lua/parley/config.lua](https://github.com/xianxu/parley.nvim/blob/main/lua/parley/config.lua) for full defaults and examples.
  210  
  211  Chat storage roots:
  212  - `chat_dir` is the primary writable root used for new chats.
  213  - `chat_dirs` is an optional list of additional roots that Chat Finder, chat validation, and chat-aware commands will scan alongside `chat_dir`.
  214  - `:ParleyChatDirs` opens a picker to add or remove chat roots at runtime.
  215  - `:ParleyChatDirAdd {dir}` adds a root directly, with directory completion.
  216  - `:ParleyChatDirRemove {dir}` removes a configured root directly.
  217  - `:ParleyChatMove {dir}` moves the current chat to another registered chat root.
  218  - The primary `chat_dir` cannot be removed at runtime.
  219  - The default shortcut for chat-root management is `<C-g>h`.
  220  
  221  For full defaults and examples, see [`lua/parley/config.lua`](lua/parley/config.lua).

   14  
   15  `make perf` opens normally attached Parley chat buffers at 100, 1,000, and
   16  5,000 lines, performs 5 warmups and 20 measured samples, and reports the real
   17  insert-event/redraw interval plus isolated timezone, footnote, decoration, and
   18  spell phases. Inclusive `edit_total` overlaps the isolated measurements; do not
   19  add or subtract the isolated phase timings as if they decomposed it.
   20

   22  `.test-tmp/perf/parley-chat-typing.json`. Override the destination (including a
   23  new parent directory) with:

   26  make perf PERF_OUTPUT=/path/to/parley-chat-typing.json

   30  `timing_unit: "milliseconds"`, `environment` (`os`, `nvim`, and the measured
   31  git `commit`), and `scenarios`. Every scenario records `name`, `phase`,
   32  `attribution` (`inclusive` or `isolated`), `line_count`, `iteration_count`,
   33  `elapsed_ms` (`samples`, `median`, `p95`), and `work`
   34  (`line_read_calls`, `lines_requested`, `full_buffer_reads`, and
   35  `structure_rows_processed`). Generated reports are ignored artifacts; durable

   39  structural bounds are correctness gates: the measured insert event must not
   40  perform a full-buffer read; decoration reads stay within the viewport/context

### What this repository is

**Certainly, `parley.nvim` is a local-first LLM research and agentic-workflow environment built as a Neovim plugin.**

It began as a Markdown chat notebook, but the repository has evolved into something broader: a keyboard-first workbench for conversations, research, file operations, document review, project knowledge, and coding-agent workflows.

Its central idea is:

> **Markdown files hold durable state; Neovim is the human interface; LLMs act as collaborators.**

### Core design

Parley deliberately keeps conversations as ordinary Markdown files:

- `💬:` marks user messages.
- `🤖:` marks assistant responses.
- `📝:` holds compact conversation memory.
- Chat metadata lives in the file header.
- Branches are linked Markdown files rather than hidden database records.
- Users can edit any part of the transcript, affecting the context supplied to subsequent model calls.

This gives the user ownership of the complete conversation state. Chats can be inspected, searched, version-controlled, edited with normal Unix tools, or passed to coding agents.

A notable feature is its **tree of chats**. You can move an exchange and its descendants into a child chat, allowing research to branch without turning the original conversation into one long, disorganized thread.

### Major capabilities

The repository currently contains several interconnected systems:

- **Multi-provider LLM chat**
  - OpenAI and compatible APIs
  - Anthropic
  - Google AI
  - Ollama
  - CLIProxyAPI, including management of a local proxy process

- **Context gathering**
  - Local files and directory patterns through `@@path`
  - Google Drive documents through OAuth
  - Provider-supported web search
  - Repository-aware artifact references

- **Conversation management**
  - Chat creation, parsing, streaming, cancellation, and regeneration
  - Branching and tree export
  - Multiple chat roots
  - Conversation memory and preference extraction
  - Searchable chat finder and outline navigation

- **Repository workbench features**
  - Markdown, note, issue, and project-vision finders
  - Ordinary-repository and “super-repo” modes
  - Repository artifact navigation
  - A discovery registry describing the kinds of documents available in a repository

- **Agent tools**
  - Safe wrappers around `ls`, `find`, `grep`, `ack`, and chat-history search
  - File reading, editing, writing, and structured edit proposals
  - Provider-neutral tool-call encoding and dispatch
  - Multi-round client-side tool execution

- **Skills**
  - Contextual term definition
  - Document review

- **Supporting modes**
  - Notes

### Architectural flow

A typical chat response probably follows this approximate route:

```text
Markdown chat buffer
        │
        ▼
chat_parser / exchange_model
        │
        ▼
chat_respond
        │
        ▼
dispatcher + provider_params
        │
        ▼
provider-specific HTTP/SSE protocol
        │
        ├── streamed text ──► render/presentation
        │
        └── tool request ───► tool_loop ───► tools/dispatcher
                                      │
                                      └── subsequent model request
```

The important architectural boundary is that provider-specific representations are translated into a common internal workflow. The same chat interface and tool system can therefore operate across different model vendors.
