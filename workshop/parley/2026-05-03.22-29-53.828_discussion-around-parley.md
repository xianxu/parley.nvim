    5  # Parley.nvim
    6  
    7  <!-- panvimdoc-ignore-end -->
    8  
    9  Parley started as a Neovim chat notebook for LLM conversations. It's created to help me research on a topic with the help with many different agents. A side goal of Parley is really a test bed for me to play with agentic coding workflow. This leading me to see a future of **markdown as state, nvim/`coding agent` as human operator interface, the beginning of future operating system for startups**. 
   10  
   11  There are just many different ways user can leverage it. With Parley, you have all the power of Neovim at your fingertips in your LLM chat, thus making comprehensive research easier. All your chat history also lives in plain markdown files, you can easily search through using local tools. You can even direct your coding agent to act according to the "brainstorming" chat thread you had with other agents, for example. The possibilities seem endless.
   12  
   13  Compared to stock chatbot, Parley supports a "tree of chats", essentially allowing user to branch of some side topic, in a linked but different file. This way, information is always organized, matching how human research and learn a topic.
   14  
   15  The philosophy behind Parley is Keep Things Simple, and Local, and a bit of Unix:
   16  - Keep chats as plain Markdown files you can edit any place
   17  - The chat transcript file has the full state of LLM chat
   18  - Highly configurable but also have good default out-of-box
   19  - Keep the workflow keyboard-first and fast
   20  - Keep behavior predictable across different chat providers
   21  - Leverage Neovim, and all its goodies
   22  - Minimal dependencies, install and it works, all you need is your API keys
   23  
   24  ## Developer performance testing
   25  
   26  Run `make perf` to collect Parley's report-only chat-typing benchmark. See
   27  [TOOLING.md](TOOLING.md#chat-typing-performance-report) for the scenario, output schema,
   28  structural correctness gates, and optional MarkdownPreview comparison.
   29  
   30  Despite of such simple interface, it's very powerful, sometimes more so than official app
   31  - You can use "any" LLM providers, mix in the same conversation input from many different LLMs
   32  - Your chat transcript can be as complex as a tree with branches, to allow you to explore into different directions, without being forced into a linear conversation
   33  - You can jump easily between such tree branches
   34  - You can access your private local file, and private Google Drive file through oauth
   35  - You can edit anything in the transcript, including LLM responses, which presumably would influence the agent's future responses, a soft prompt engineering. You are constructing an understanding of a topic together with the help of LLMs
   36  - All you chat history in one place locally, you can search and further refine with whatever tools you want
   37  - Tweak system prompts to best suit your needs
   38  - Have many different chat threads active in different vim buffers, terminals etc., no limits
   39  - Easily switch between different chat threads, instant search experience with Chat Finder <C-g>f anywhere in Neovim
   40  - Also a good learning tool for LLM interactions, e.g. in raw request/response modes, you see all request/response details
   41  - New LLMs support web search and grounding, you can easily enable or disable if you want it to be faster
   42  - Publish your chat as markdown or HTML, for blogging or sharing, e.g. [a chat about async programming](https://xianxu.github.io/2025/05/12/conversation_around_concurrent_programming_models.html)
   43  - Share your brainstorming transcripts with your coding agents to start materializing it!

  104  ## First 60 Seconds
  105  
  106  1. Run `:ParleyChatNew` (default shortcut: `<C-g>c`) to create a new chat.
  107  2. Type your question after `💬:`, no need for anything else. `Topic: ?` will be automatically filled with summary of your question.
  108  3. Run `:ParleyChatRespond` (default shortcut: `<C-g><C-g>`) with mouse on the question line.
  109  4. Get a response from the agent after `🤖:`, streaming in real time. A slow
  110     start shows a playful virtual progress line after one second; it never enters
  111     the Markdown transcript.
  112  
  113  A Parley chat is a normal markdown file with a header and alternating `💬:` / `🤖:` blocks.

  115  ## Basic Commands
  116  
  117  Most-used defaults:
  118  
  119  **Global**
  120  - `<C-g>c` new chat - global hotkey
  121  - `<C-g>f` find chat - opens immediately with a cancellable animated
  122    `scanning…` row while Chat Finder asynchronously discovers chat headers; an
  123    exact background prewarm is reused when available
  124  - `<C-n>f` find notes - the same immediate loading experience over recursive
  125    note metadata; note bodies are not read, and special folders still bypass
  126    recency filtering
  127  - `<C-y>f` find issues - asynchronously read issue/history metadata with
  128    vocabulary-backed ordering and repository facets in super-repo mode
  129  - `<C-j>f` find vision initiatives - asynchronously read YAML file bundles,
  130    preserving file/parser order and exact source-line jumps
  131  - `<C-g>m` find Markdown files - directory facets in ordinary repo mode and
  132    repository facets in super-repo mode; query text and facet choices persist
  133    across finder reopenings within the current Neovim session. When a facet bar
  134    wraps beyond its visible height, point at the bar and use the mouse wheel to
  135    reach the remaining facets. The picker opens immediately with a cancellable
  136    animated `scanning…` row while Git discovers all tracked Markdown files plus
  137    untracked, non-ignored Markdown files; ignored untracked files and Markdown
  138    inside nested repositories or submodules are excluded from the parent scan.
  139  - `<C-g>p` toggle peer (super-repo) mode - aggregate reads across sibling
  140    `.parley` repositories. The explicit repo/peer choice persists separately for
  141    each repository; an unsaved repository starts in ordinary repo mode.
  142  
  143  **In Chat Buffer**
  144  - `<C-g>?` show key bindings
  145  - `<C-g><C-g>` respond
  146  - `<M-CR>` respond (normal/insert); **visual-select a phrase + `<M-CR>`** → inline term definition — immediately shows a spinner after the selection, then on success replaces it with a markdown footnote reference/footer and centered diagnostic float, honoring `:ToggleWebSearch` for unfamiliar terms
  147    - Reopened chats recover multi-word highlights from structured footnotes such as `[^acos]: "Advertising Cost of Sales". Ratio...`; generated ids such as `[^serverless-functions]` also recover `serverless functions` from the slug when that phrase appears before the reference.
  148  - `<C-g>G` respond all
  149  - `<C-g>x` stop
  150  - `u` / `<C-r>` undo/redo normally; while a response is pending, Parley asks
  151    before cancelling that buffer's request and changing history (default: No)
  152  - `<C-g>t` chat outline
  153  - `<C-g>a` change agent
  154  - `<C-g>P` next system prompt
  155  - `<C-g>s` skill picker (review, voice-apply, etc.)
  156  - `<C-g>b` branch/prune - move the current exchange and following exchanges to
  157    a child chat
  158  
  159  Tool-fold toggling is configurable but unbound by default. To opt in, set
  160  `chat_shortcut_toggle_tool_folds = { modes = { "n" }, shortcut = "<leader>tf" }`.
  161  
  162  Parley manages folds inside a chat buffer: tool calls, tool results, summaries
  163  and thinking blocks fold, and questions never do. It owns **every** fold within
  164  an exchange — including the tail of the buffer after the last block — so a
  165  manual `zf` there is removed the next time that exchange is reconciled. Folds
  166  outside every exchange (the frontmatter, for instance) are left alone.
  167  - `<C-g>l` toggle follow cursor
  168  - `<C-g>i` to insert a fork in the chat tree, can be inline or standalone
  169  - `gf` smart go-to-file: on an ariadne artifact ref (`ariadne#11`, `#15 M4`, `pair#84`) resolves it and jumps (family picker when it resolves to many); on a plain path, Vim's native `gf`
  170  
  171  **Corresponding commands**
  172  - `:ParleyChatNew` create a new chat
  173  - `:ParleyChatFinder` asynchronous chat finder with joinable metadata prewarm
  174  - `:ParleyNoteFinder` asynchronous recursive note finder with joinable metadata prewarm
  175  - `:ParleyIssueFinder` asynchronous issue/history finder
  176  - `:ParleyVisionShow` asynchronous project-initiative finder
  177  - `:ParleyMarkdownFinder` asynchronous Git-aware Markdown finder with contextual directory/repository facets
  178  - `:ParleyChatRespond` answer current question
  179  - `:ParleyChatRespondAll` regenerate from start to cursor
  180  - `:ParleyStop` stop running generation
  181  - `:ParleyOutline` display questions in this buffer for navigation
  182  - `:ParleyKeyBindings` show active Parley keyboard shortcuts
  183  - `:ParleyAgent` switch agent
  184  - `:ParleySystemPrompt` switch system prompt
  185  - `:ParleyToggleFollowCursor` toggle live cursor-follow during streaming
  186  
  187  All five disk-backed finders open their picker shell immediately and keep the
  188  prompt live while `scanning…` animates. Settled results replace the loading row
  189  in one update; partial failures retain usable rows with a warning, total failure
  190  leaves a nonselectable error, and Esc cancels picker-owned work. Markdown uses
  191  Git's tracked union untracked-nonignored boundary, so ignored vendor trees are
  192  not searched in either ordinary or super-repo mode.

  194  ## What Parley Supports
  195  
  196  - Providers: OpenAI, Anthropic, Google AI, Ollama, OpenAI-compatible endpoints, and CLIProxyAPI.
  197    - parley can **manage a local `cliproxyapi`** for you — it renders the config from Lua and lazily starts/reuses/health-checks the proxy. `:ParleyProxy status|start|stop|restart|models <provider>|providers|login <provider>|reap|update` (bare `:ParleyProxy` prints per-subcommand help). **On by default but dormant** — only acts when a cliproxyapi-provider agent runs, and reuses an existing proxy if one is up; a fresh machine needs `brew install cliproxyapi` + a one-time `:ParleyProxy login`. Set `cliproxy = { manage = false }` to opt out. See [atlas/providers/cliproxy-managed.md](atlas/providers/cliproxy-managed.md).
  198    - **Live models in the agent picker** — cliproxyapi already advertises what it serves, and that set moves on its own (an antigravity login registers new models with no restart), so parley reads that catalog instead of asking you to name models in Lua. Below your configured agents the picker shows a `── live · cliproxy ──` section; picking a row gives you a tool-enabled agent for that model, and it survives a restart. `<C-a>` expands to the whole catalog. A provider you are not logged into shows as `(logged out)` — selecting it starts the login. Configure which providers appear, and how many models each contributes, with `cliproxy.live_models = { providers = { "claude:opus,sonnet", "codex:gpt-5.6", "antigravity" }, per_provider = 3 }`: an entry is `"<provider>[:<term>,…]"`, the terms are substrings matched against the model id and its display name, and omitting `providers` offers every provider parley knows. It names providers and model families, never versions, so it does not go stale.
  199  - File context with `@@path/to/file` and directory patterns.
  200  - Web search toggle for supported providers, with semantic search/reasoning status shown in the response's transient virtual progress line.
  201  - Outline navigation, highlighting.
  202  - Export chat to markdown or HTML, for blogging, e.g. [a chat about async programming](https://xianxu.github.io/2025/05/12/conversation_around_concurrent_programming_models.html).
  203  - Misc: notes, interview mode, raw mode, and export.

  205  ## Configuration Entry Points
  206  
  207  Common options live in `setup()`:
  208  - `api_keys`
  209  - `chat_dir`
  210  - `notes_dir`
  211  
  212  Merge behavior in `setup(opts)`:
  213  - `agents`, `system_prompts`, and `hooks` are merged by key/name, so you can override only selected entries.
  214  - Most other top-level keys are replaced when provided (for example `chat_dir`, `chat_dirs`, `notes_dir`, `chat_template`, `raw_mode`, `highlight`, `chat_memory`, `providers`, `api_keys`).
  215  - Practical rule: for non-merged tables, provide the full table you want, not just one nested field.
  216  - Reference [lua/parley/config.lua](https://github.com/xianxu/parley.nvim/blob/main/lua/parley/config.lua) for full defaults and examples.
  217  
  218  Chat storage roots:
  219  - `chat_dir` is the primary writable root used for new chats.
  220  - `chat_dirs` is an optional list of additional roots that Chat Finder, chat validation, and chat-aware commands will scan alongside `chat_dir`.
  221  - `:ParleyChatDirs` opens a picker to add or remove chat roots at runtime.
  222  - `:ParleyChatDirAdd {dir}` adds a root directly, with directory completion.
  223  - `:ParleyChatDirRemove {dir}` removes a configured root directly.
  224  - `:ParleyChatMove {dir}` moves the current chat to another registered chat root.
  225  - The primary `chat_dir` cannot be removed at runtime.
  226  - The default shortcut for chat-root management is `<C-g>h`.
  227  
  228  For full defaults and examples, see [`lua/parley/config.lua`](lua/parley/config.lua).

    1  # Tooling
    2  
    3  ## Development Commands
    4  - Manual testing: Start Neovim and use `:lua require('parley').setup()` followed by `:Parley`
    5  - Run tests: `make test` (runs all unit + integration tests via plenary.nvim in headless Neovim)
    6  - Lint: `make lint` (requires `luacheck`; see install note below)
    7  - Run tests for one spec: `make test-spec SPEC=chat/lifecycle` (uses `atlas/traceability.yaml` mapping)
    8  - Run tests for changed specs: `make test-changed` (runs mapped tests for changed `atlas/*/*.md` files), this is faster than full test run
    9  - Run the report-only real chat-typing benchmark: `make perf` (details below).
   10  - Refresh SSE fixtures: `ANTHROPIC_API_KEY=... OPENAI_API_KEY=... make fixtures`
   11  - Test files live in `tests/unit/` (pure logic, no Neovim APIs) and `tests/integration/` (full Neovim runtime)
   12  
   13  ## Test Scratch Directories
   14  
   15  The harness gives every run its own `HOME`, `XDG_*`, and `TMPDIR` so tests never
   16  touch your real config. Those trees live **outside the repo**, under
   17  
   18  ```
   19  $TMPDIR/parley-test-env/<checkout-name>-<cksum-of-path>/{home,xdg,tmp}
   20  ```
   21  
   22  Print the resolved path with `make -n test-clean-env`, or override the whole
   23  root with `make test TEST_ENV_ROOT=/some/where`.
   24  
   25  They sit outside `$(CURDIR)` deliberately (#202). Eight parallel jobs create and
   26  delete entries in the scratch tmp dir for the whole run, while the `find`/`grep`/
   27  `ack` tool specs traverse the repo to exercise the real tree — and one of them,
   28  `grep`'s "defaults missing path to cwd", cannot be written any other way. When
   29  the scratch lived in `.test-tmp/`, those specs raced a directory vanishing
   30  mid-traversal and `find` exited nonzero, which read as an unrelated flake.
   31  Keeping the churn out of the tree the specs walk is what makes the suite
   32  deterministic; no spec has to defend itself.
   33  
   34  `make test` runs `make test-clean-env` first, so each full run starts from an
   35  empty root. It removes the `home`, `xdg`, and `tmp` leaves under the root — never
   36  the root itself — so pointing `TEST_ENV_ROOT` at a directory holding anything
   37  else is safe. It also removes the pre-#202 in-repo `.test-home`, `.test-xdg`,
   38  and `.test-tmp` directories if they are still around.
   39  
   40  Run only one `make test` per checkout at a time: a second concurrent run deletes
   41  the first's scratch, loudly. Use a separate worktree (the root is keyed by
   42  checkout) or a distinct `TEST_ENV_ROOT` for concurrent suites.
   43  
   44  ## Chat-Typing Performance Report
   45  
   46  `make perf` opens normally attached Parley chat buffers at 100, 1,000, and
   47  5,000 lines, performs 5 warmups and 20 measured samples, and reports the real
   48  insert-event/redraw interval plus isolated timezone, footnote, decoration, and
   49  spell phases. Inclusive `edit_total` overlaps the isolated measurements; do not
   50  add or subtract the isolated phase timings as if they decomposed it.
   51  
   52  The command prints median/p95 timings and scaling ratios, then overwrites
   53  `$(TEST_TMP)/perf/parley-chat-typing.json` — see *Test Scratch Directories*
   54  above for where that resolves. The default path is inside the `tmp` leaf that
   55  `make test` wipes, so a report left there does not survive the next test run;
   56  pass `PERF_OUTPUT` to keep one. Override the destination (including a new parent
   57  directory) with:
   58  
   59  ```sh
   60  make perf PERF_OUTPUT=/path/to/parley-chat-typing.json
   61  ```
   62  
   63  The JSON envelope has `schema_version: 1`, `generated_at`,

### Approach

I inspected the repository structure, README, architecture/atlas documentation, primary Lua entry points, provider dispatcher, configuration, and test layout. I have **not** run the plugin or its test suite, so behavioral conclusions are based on code and documentation rather than runtime verification.

### What this repository is

**Parley.nvim is a local-first, Markdown-native LLM workspace inside Neovim.**

It began as a chat notebook, but its ambition is broader than “ChatGPT in Vim.” The repository treats:

- Markdown files as persistent application state
- Neovim as the human operating interface
- LLM providers and coding agents as collaborators
- Linked chats, notes, issues, and plans as a navigable knowledge graph

The central idea is that conversations should remain ordinary, editable files rather than opaque records trapped inside a web application.

A typical chat looks conceptually like:

```markdown
---
topic: Example topic
agent: SomeAgent
---

💬: A question from the user

🤖: A streamed response from the model

📝: Optional conversation memory or summary
```

Because the transcript contains the conversation state, users can edit previous questions or answers, search them with ordinary tools, put them under version control, and give them to another coding agent.

### What makes it distinctive

#### Tree-shaped conversations

Parley supports branching a conversation into linked child files. This avoids forcing research into one increasingly long linear transcript.

When responding within a child conversation, Parley can reconstruct relevant exchanges from its ancestor chain. That behavior is visible in `chat_respond.lua`, particularly its ancestor-message construction and parent-link traversal.

This is probably the repository’s most important conceptual feature: **conversation structure is represented through links among Markdown files rather than hidden database records.**

#### Multiple LLM providers

The plugin supports:

- OpenAI
- Anthropic
- Google AI
- Ollama
- OpenAI-compatible endpoints
- CLIProxyAPI

The internal dispatcher provides a common request path while provider adapters handle differences in:

- Request payloads
- Streaming formats
- Server-side web-search tools
- Client-side tool encoding
- Error recovery
- Message translation

The provider abstraction is more sophisticated than a simple endpoint switch. In particular, the tool layer translates historical tool messages into the provider’s expected wire format before each request.

#### Client-side tools

Agents can use locally implemented tools such as:

- `read_file`
- `write_file`
- `edit_file`
- `propose_edits`
- `ls`
- `find`
- `grep`
- `ack`
- `chat_history_search`

These live under:

```text
lua/parley/tools/
├── dispatcher.lua
├── serialize.lua
├── wire.lua
├── wire_anthropic.lua
├── wire_openai.lua
└── builtin/
```

The design deliberately separates:

1. Tool definitions
2. Tool execution
3. Provider-specific serialization
4. The iterative tool-call loop

That is a sound architectural boundary because OpenAI-compatible and Anthropic APIs represent tool calls differently while the local operation should remain provider-independent.

#### Repository-aware knowledge work

Parley extends beyond chat into:

- Chat and note finders
- Git-aware Markdown discovery
- Local issue management
- Vision/initiative tracking
- Repository artifact references
- Cross-repository or “super-repo” discovery
- Export to Markdown and HTML
- Google Drive and OAuth-backed references
- Document review and voice-application skills

This makes the plugin resemble a **knowledge-work environment built on Neovim**, with chat as its primary interaction model.

### Main runtime flow

The core path appears to be approximately:

```text
require("parley").setup(opts)
        │
        ├── merge configuration and defaults
        ├── register providers and secrets
        ├── initialize commands and keybindings
        ├── initialize finders, skills, notes, issues, and UI
        │
User invokes :ParleyChatRespond
        │
        ├── parse the Markdown transcript
        ├── identify the current exchange
        ├── collect ancestor conversation context
        ├── resolve @@ file or remote references
        ├── select agent, model, prompt, and tools
        ├── construct internal messages
        │
parley.dispatcher
        │
        ├── translate messages to provider wire format
        ├── construct provider payload

        ├── decode SSE events
        │

        │
        ├── decode tool calls
        ├── execute local tools
        ├── append tool results

        │
chat presentation
        │

        ├── update transient progress
        ├── reconcile folds and decorations
        └── finalize transcript state
```

### Important source areas

#### `lua/parley/init.lua`

This is the main composition root. It:

- Holds top-level plugin state
- Connects modules to the central Parley object
- Registers commands and keybindings
- Initializes notes, chats, finders, skills, issues, exports, and repository modes
- Exposes the public API

At roughly 160 KB, it is also a significant architectural concentration point.

#### `lua/parley/chat_parser.lua`

This handles the Markdown transcript as a structured model:

- Headers
- Questions
- Answers
- Summaries and reasoning
- Tool blocks
- Branch links
- Exchange boundaries

Parsing correctness is critical because the Markdown buffer is both user-facing text and application state.

#### `lua/parley/chat_respond.lua`

This owns most of the response pipeline:

- Building conversation messages
- Incorporating ancestor exchanges
- Resolving context references
- Starting and stopping responses
- Processing follow-up tool turns
- Handling failures
- Updating the active chat

At roughly 105 KB, this is another major complexity hotspot.

#### `lua/parley/dispatcher.lua`

This is the transport boundary. It:

- Configures provider adapters
- Moves secrets into the vault
- Creates provider-specific payloads
- Translates tool messages
- Starts requests
- Processes streamed events
- Coordinates recovery from provider failures

#### `lua/parley/providers.lua`

This appears to hold the concrete provider behavior: payload formatting, response parsing, headers, and provider-specific web-search integration.

#### `lua/parley/exchange_model.lua`

The atlas describes this as the positional source of truth for the buffer:

> Everything is a block.

That is an important design decision. Features such as folds, highlighting, review markers, and streaming edits need a shared interpretation of where each logical exchange component begins and ends.

They power chat, note, issue, vision, and Markdown discovery. The README emphasizes immediate picker display, cancellable background scanning, partial-failure handling, and cached prewarming.

### Development and quality strategy

The project has a notably extensive testing setup for a Neovim plugin.

Main commands include:

```sh
make test
make lint
make test-spec SPEC=chat/lifecycle
make test-changed
make perf
```

The test suite includes three meaningful levels:

- **Unit tests:** parsing, serialization, provider translation, finders, tools, configuration, and pure logic
- **Integration tests:** real buffer behavior, streaming, tool loops, proxy lifecycle, exports, folds, and skills
- **Architecture tests:** broad invariants such as controlled buffer mutation and performance-sensitive line access

The performance harness measures chat typing at 100, 1,000, and 5,000 lines. Its correctness gates prohibit full-buffer reads during ordinary insert events and check that structural processing remains bounded. This suggests that performance problems in long Markdown chats have received deliberate attention.

Tests run with isolated `HOME`, `XDG_*`, and temporary directories outside the repository. That avoids tests touching real user configuration and prevents filesystem races when tests traverse the repository.

### Architectural strengths

#### Plain files are genuinely central

“Local-first Markdown” does not appear to be merely a storage format added around an otherwise database-oriented system. Parsing, branching, exporting, searching, and context reconstruction are all built around files as the canonical state.

#### Provider differences are acknowledged

The repository does not pretend all LLM APIs are interchangeable. It isolates provider-specific transport and tool-wire behavior while preserving a provider-neutral internal model.

#### Features have traceability

The combination of:

- Atlas entries
- Implementation mappings
- Unit tests
- Integration tests
- Architecture-level tests

makes it easier to understand why a feature exists and what protects its behavior.

#### UX receives systems-level attention

The asynchronous finders, transient progress display, cancellation handling, folding rules, stream finalization, cursor-follow behavior, and long-buffer performance indicate that the project treats editor behavior as core product functionality rather than decoration.

#### Tool execution has explicit safety seams

Local tools are defined and tested individually, and editing supports proposed changes rather than requiring unrestricted arbitrary shell execution. This does not eliminate risk, but it provides clearer control boundaries.

### Potential weaknesses and risks

#### The composition root is very large

`init.lua` is approximately 160 KB. Although functionality has been extracted into modules, it still appears to coordinate a large amount of state and behavior.

This can lead to:

- Implicit coupling through the central `M` object
- Difficult initialization ordering
- Modules depending on mutable shared state
- Harder isolated testing
- Unclear ownership of cross-cutting behavior

The pattern of calling `module.setup(M)` is practical for a Lua plugin, but it resembles dependency injection through a service locator. It should be watched as the project grows.

#### The response pipeline remains concentrated

`chat_respond.lua` is approximately 105 KB. Responding involves inherently complex orchestration, but this size suggests that context resolution, message construction, buffer lifecycle, tool continuation, and provider execution may still be too tightly grouped.

#### Configuration has become operationally complex

The defaults now cover:

- Multiple providers
- Local proxy management
- Automatic binary download
- OAuth
- Live model catalogs
- Tool routing
- Web-search strategies
- Agents
- Prompts
- Chat and note roots

The comment that users should begin with minimal configuration is sensible, but maintaining backward compatibility and understandable merge semantics will probably remain difficult.

One particularly important trust boundary is automatic downloading of a local proxy executable. The configuration comments recognize this as a security decision, which is good, but distributions or cautious users may prefer explicit opt-in.

#### Documentation layers are uneven

`README.md` and `atlas/` are detailed, while `ARCH.md` is only a few lines. The atlas effectively serves as the real architecture document.

That is workable, but a new contributor may not immediately know:

- Which modules form the stable core
- Which are experimental
- Where shared state is owned
- Which dependency directions are intentional
- Which invariants are architectural rather than incidental

#### Scope is expanding rapidly

Parley now includes chat, notes, issue management, vision tracking, discovery, skills, review workflows, repository aggregation, proxy management, and OAuth integrations.

That supports the larger “operating environment for knowledge work” vision, but it also creates a product-identity risk: the plugin could become harder to understand if new subsystems do not remain subordinate to its Markdown-native conversation model.

### My overall assessment

**Certainly, this is no longer a small chat plugin.** It is an ambitious Neovim-based environment for AI-assisted research and software work.

Its strongest coherent idea is:

> Markdown is durable shared state, Neovim is the operator interface, and LLMs are interchangeable collaborators acting over that state.

The implementation shows signs of a mature, actively evolved project:

- Broad feature coverage
- Considerable automated testing
- Provider-aware tool handling
- Explicit performance work
- Detailed feature documentation
- Attention to real editor lifecycle problems

Its principal architectural challenge is likely **managing complexity without losing the simplicity promised by the file-based model**. The repository already contains good modular seams, but several oversized orchestration modules and a rapidly broadening feature surface suggest that ownership boundaries will need continued refinement.
