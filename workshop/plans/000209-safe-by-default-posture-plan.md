## Proposed behavior and approval decisions

Recommended: `tool_read_roots = {}`, `memory_prefs.enable = false`, and
`cliproxy.auto_download = false`; retain `cliproxy.manage = true`.
`ParleyProxy update` explicitly authorizes download. A valid
`ParleyProxy login PROVIDER` with a missing binary installs it, then starts that
login, with a visible download notice and a cancel action. Selecting a clearly
labelled first-use “Install CLIProxyAPI and log in” action is equivalent.
Opening Neovim, a chat, a model picker, health/status/help, or discovering a
binary does not authorize installation. Sending a message with a missing binary
returns actionable installation/login instructions without sending user data.
Status and picker opening read local/cache data only; unknown or stale data is
labelled honestly. `ParleyProxy status refresh` explicitly authorizes status
probes/latest-release lookup; a labelled picker “Refresh models” action authorizes
catalog HTTP. Neither action creates a secret/config/binary or starts a proxy.
An absent credential is reported as unavailable, not generated by observation.
Existing `auto_download = true` remains explicit configuration authorization,
but uses the same asynchronous owner. Unknown login providers are refused
before install, filesystem mutation, or network access.

Alternatives considered: keep a separate mandatory update command before login
(smaller change but weak new-machine UX); ask another confirmation after every
explicit login (adds a redundant step). The recommendation treats a documented
login command as authorization for its required installation, matching the
operator's deployment goal. This behavioral expansion needs approval.

Directory acceptance replaces the historical “no file outside chat_dir” claim,
which excludes legitimate state/log/cache files. With #211 merged, a fresh
`NVIM_APPNAME=parley` profile permits only Parley-owned state/cache/log leaves
beneath that profile's `stdpath` roots during startup; no chat, note, export,
proxy bin/auth/config/secret or repository artifact directory is created before
its owning action. Merely configuring a destination is not use. Explicit
custom destinations take effect when that feature is used. Credentials are
created only by install/start/login paths that need them; auth storage relocation
is not part of #209. Plugin-manager bootstrap is a separate, explicit install
step; the no-egress invariant starts with dependencies already installed.

Default startup and passive UI perform zero HTTP/DNS requests, start no proxy or
login process, and send no chat data. Observe startup through at least the
existing two-second deferred memory window and execute pending callbacks before
asserting. Model requests, explicit login/install/update, and enabled preference
generation have their existing explicit authorization boundaries.

## Core concepts

### Pure entities

| Name | Lives in | Status |
|------|----------|--------|
| install_transition | lua/parley/cliproxy_install.lua | new |

`install_transition(state, event)` owns one installation operation's legal
states and effects: idle, resolving, downloading, verifying, extracting,
committing, terminal. It receives results, never performs IO. Terminal events
are idempotent; stale operation ids produce no effects. One operation owns one
staging directory and at most one subprocess. Keep release parsing and update
policy in existing cliproxy_release/cliproxy_config functions (ARCH-DRY/PURE).
No generalized task framework or second release-selection policy.

### Integration points

| Name | Lives in | Status | Wraps |
|------|----------|--------|-------|
| download | lua/parley/cliproxy.lua | modified | asynchronous release/checksum/archive/install IO |
| update | lua/parley/cliproxy.lua | modified | asynchronous selection/install plus existing restart |
| ensure_running | lua/parley/cliproxy.lua | modified | authorized missing-binary install then spawn |
| login_argv | lua/parley/cliproxy.lua | modified | validate provider before any install-related effect |
| managed_binary | lua/parley/cliproxy.lua | modified | read-only installed binary discovery |
| status | lua/parley/cliproxy.lua | modified | local snapshot versus explicitly requested network refresh |
| open | lua/parley/agent_picker.lua | modified | cached model list and explicit refresh action |
| install_for_login | lua/parley/cliproxy.lua | new | validated login intent through installer to login argv |

The command branch in init.lua calls install_for_login, then preserves existing
callback-port preflight and run_login. UI callers use callbacks throughout;
remove synchronous downloader callers rather than maintain a second installer.
Existing release fixtures persist versions, latest pointer, checksums and request
history; extend their slow mode with controllable release completion/failure.
Existing fake_cliproxy preserves installed/running version and login behavior.
No public network is required for automated tests (ARCH-MOCK).

## Operating envelope and lifetime

Startup performs no network work. UI-triggered transfer/hash/extract/version
probes use asynchronous subprocesses; a scheduled heartbeat must run while a
slow fixture has a transfer pending. Retain existing transfer timeouts (300s
archive, 30s checksum, bounded release lookup) and existing restart deadline;
local subprocesses get finite deadlines too, selected and documented from the
current helpers before implementation. One install/update operation per profile
is admitted; concurrent callers receive “installation already running,” rather
than racing the same staging directory. A filesystem lock covers separate
Neovim instances; use owner pid plus operation identity, and reclaim only a
verifiably dead same-host owner. Unknown ownership refuses visibly.

State/event policy (ARCH-ORDER): second request refuses; cancellation and
VimLeavePre terminate the active subprocess, prevent continuation/restart/login,
and clean the operation's temporary files; late callbacks are ignored.
Process death leaves the previous installed binary usable and at most one
operation staging tree; the next explicitly authorized install reclaims a dead
owner's residue. Cancellation during final atomic commit reports the observed
installed outcome rather than claiming rollback. Restart failures keep the
successfully installed binary and report the existing warning semantics.

Archive, staging, lock and version-record temporary files have one owner and
cleanup on success/failure/cancel; cleanup failure is reported with the primary
result (ARCH-FUNERAL). Preserve validated versions, checksum refusal, atomic
rename and malformed version-record handling. Download sources remain the
existing HTTPS release origin; checksums are integrity checks, not independent
authenticity evidence. Fake endpoints remain test-mode gated. Never copy real
credentials or access real HOME in fixtures (ARCH-SECURE).
