## Answers and gaps

1. **Install the app and ask the first question — answerable.** On macOS run `brew install xianxu/parley/parley`, then `parley`. First launch installs editor dependencies and opens Welcome. Connect when prompted or run `:ParleyProxy connect`, choose a model with `:ParleyAgent`, press `i`, type after 💬:, then Option+Enter; `:ParleyChatRespond` is the command alternative. Escape enters Normal mode for commands. Sources: `README`, `tutorials/welcome`, `atlas/infra/packaging`. Minor gap: supported macOS versions/architectures and an accessible first-install-failure procedure are not specified in these topics; the app/recovery guide links point outside the catalog.

2. **App versus plugin settings/chats/logins — partially answerable.** App configuration is `~/.config/parley/init.lua` or `$XDG_CONFIG_HOME/parley/init.lua`; it uses an isolated `NVIM_APPNAME=parley` profile, with chats directly under that profile's `chats/`. Plugin users call `require('parley').setup(opts)` from their existing Neovim config and control `chat_dir`; app and plugin share `~/.cli-proxy-api` account JSON. Project chats live under `<project>/workshop/parley/`. Sources: `atlas/infra/config`, `atlas/infra/starter`, `atlas/infra/repo_mode`, `atlas/infra/vault`. Gap: the complete default absolute app chat/data/state/cache paths, plugin default chat path, and XDG equivalents are not in the catalog. “Under its profile” is insufficient to locate a backup. The linked `packaging/starter-config/README.md` is not a listed topic.

3. **Change model/account — model answerable, account partial.** `:ParleyAgent` picks a model, `:ParleyAgent NAME` selects a configured agent, and `:ParleyNextAgent` / Ctrl+g a cycles. Selection persists in `state_dir/state.json`; `default_agent` may override it. `:ParleyProxy connect` or `:ParleyProxy login PROVIDER` connects an account; a logged-out provider row also starts login. Sources: `atlas/providers/agents`, `atlas/providers/cliproxy-managed`, `tutorials/welcome`. Gap: choosing between two already connected accounts of the same provider, determining which account will serve a request, signing out, and replacing an account are not documented as user actions. README's “choose ... connected account” is broader than the described provider/model selection UI. Per-chat model/provider header fields are listed in `atlas/chat/format`, but their interaction with changing the picker selection is not explained precisely.

4. **YAML-list tags missing — answerable.** The header parser accepts single-line comma/whitespace-separated tags such as `tags: tutorial, ai`; block YAML and bracketed YAML lists are unsupported. Keep metadata and its closing separator in the first ten lines, save, then reopen Finder. Check tag/root filters and recency; `[]` means untagged. Sources: `atlas/chat/format`, `atlas/ui/pickers`. No material gap for this question.

5. **Branch destination and outline navigation — mostly answerable.** In a chat, Option+i / Ctrl+g i inserts a branch link, saves the parent, creates and opens the child at its first question in Insert mode. A visual selection seeds “tell me more about ...”; plain branching leaves a question for the user. Option+t / `:ParleyOutline` navigates the linked tree: branch rows open the child at line 1; questions/markers jump to their line; choosing an item in the parent returns there. Foreign Markdown inserts a reference but neither creates the child nor saves the parent. Sources: `tutorials/basics`, `tutorials/advanced`, `atlas/chat/inline_branch_links`, `atlas/ui/outline`. Gap: the physical directory chosen for a child branch is not explicitly stated; the new-chat primary-directory rule in `atlas/chat/lifecycle` is not enough to prove branch behavior, especially for a parent opened from another root. The detailed no-focus-change landing condition is documented, but beginner tutorials omit that an in-flight response refuses branching.

6. **Do Markdown headings appear in chat outline? — answerable.** No. Chat outlines show questions, `@@...@@` markers and branches; ordinary Markdown outlines include #, ##, ### headings. Sources: `tutorials/basics`, `tutorials/advanced`, `atlas/ui/outline`. Minor gap: tutorial prose says Markdown headings generally, while the reference explicitly lists only levels 1–3; levels 4–6 should not be promised.

7. **What the model receives / lock exclusion — answerable with context precision gaps.** A request contains the selected question and relevant preceding exchanges, resolved system instructions, included file contents/images/tool results, and ancestor context for child chats. Later exchanges and the pre-first-question preamble are excluded. Full-line 🔒: and 🌿: markers exclude exactly that one line; inline branch links retain their display text. Lock notes remain local plaintext and may be exposed if a file tool reads the transcript; editing does not revoke data already sent. Sources: `tutorials/advanced`, `atlas/chat/parsing`, `atlas/chat/lifecycle`, `atlas/chat/inline_branch_links`, `atlas/infra/starter`. Gaps: “relevant” ancestor context is not specified with an exact branch-position cutoff. `atlas/chat/lifecycle` says summaries replace full ancestor answers “when available,” while `atlas/chat/memory` says full history is retained with memory off; whether the latter includes ancestors is unclear. The `@@` inclusion reference documents syntax and navigation bases, but does not clearly state the resolution/permission rules for content inclusion itself (`atlas/context/file_references`); do not assume the editor-open rules equal file-tool rules.

8. **Automatic memory summaries/preferences — answerable, with a cross-root contradiction.** Both `chat_memory.enable` and `memory_prefs.enable` default false. Answer-style 📝 summaries are enabled but do not activate memory truncation or preference generation. Enabling memory keeps a recent full-exchange window and substitutes older exchanges; preferences separately enable background generation and later system-prompt injection. A per-chat window header alone does not enable memory. Sources: `atlas/infra/starter`, `atlas/chat/memory`, `atlas/chat/memory_prefs`, `tutorials/advanced`. Contradiction: `atlas/chat/memory` says chat-history search covers ALL configured roots, but starter/tutorials constrain it through allowed roots/current project. The manual `:ParleyMemoryPrefs` command is described without saying whether it works when the feature is disabled.

9. **Customize/disable shortcut and get current help — answerable, with misleading shorthand.** Supply an option table such as `chat_shortcut_drill_in = { shortcut = "<M-z>" }`; `shortcut` can be a list of aliases; `shortcut = ""` or `{}` disables the action. `default_keymaps = false` disables implicit bindings while explicitly supplied shortcuts remain. Open `:ParleyKeyBindings` / Ctrl+g ? for current configured context. This does not inspect arbitrary later mappings from user Lua or other plugins. Reopen an already prepared buffer after changes; its binding decision is sampled on preparation. Sources: `atlas/ui/keybindings`, `atlas/infra/config`. Gap/ambiguity: config's “Shortcut options accept a string or a list” can be read as assigning a bare string to `chat_shortcut_*`, but keybindings explicitly says a bare-string config value falls back to the default; the nested `shortcut` shape should appear in the short config guide. Disabling an action differs from removing one alias, despite “disable one binding” wording. App customization location is named, but a complete example preserving starter options is absent.

10. **Finder aliases and reserved controls — answerable.** Every allowed resolved alias is installed in prompt Insert/Normal and results Normal modes. Reserved Enter/Escape aliases are rejected individually so an allowed sibling alias still works. Fixed prompt controls (Ctrl+j/Down, Ctrl+k/Up, Enter, Esc/Ctrl+c) survive `default_keymaps=false` and have a separate help section. Sources: `atlas/ui/keybindings`, `atlas/ui/pickers`. Gaps: exact reserved key spellings and alias-conflict precedence are not enumerated; “existing collision precedence is unchanged” cannot teach a new user which action wins. Help's exact treatment of rejected configured aliases is not made explicit. The scope forest lists only three finder-specific scopes even though other pages describe five finders; current-help coverage for Markdown/Vision finders is less discoverable.

11. **Image paste, limits, export dependencies — answerable with limit/dependency ambiguity.** Copy an image, place the cursor in a question in a new timestamp-named chat, press Option+v, use an image-capable model and send. Images are stored in `assets/<chat-id>/`; attachment links must occupy a whole question line and use the documented local asset shape. Clipboard PNG recipes use osascript on macOS or wl-paste/xclip on Linux. Optional shrink converts eligible large images; budgets are documented as 10 MB/image, 20 MB encoded/request, 20 images/request, newest first; dropped images get a note. Tree export copies assets; HTML needs neighboring assets and loads highlight.js from a CDN. Markdown export uses Jekyll conventions and its asset URLs need adjustment for `_posts/`. Sources: `tutorials/advanced`, `atlas/chat/attachments`, `atlas/export/formats`, `atlas/export/tree_export`, `atlas/infra/dependencies`. Gaps: the attachment page alternates 10 MiB “source cap” and 10 MB “per image” without explaining units/stages, so an exact accepted byte size is unsupported. Dependency docs call pandoc optional and mention an exporter pandoc error, but neither export guide states which export needs pandoc or the install command. Image-capable model discovery is left to the user. Stable tutorial chats are recognized chats but paste requires a timestamp; the tutorial wisely says start a new chat, though this reason is not prominent. Auto-shrink blocks up to five seconds according to the reference, which qualifies the paste-flow's async description.

12. **Web-search defaults/support/indicators — answerable.** Enabled by default; saved toggle wins. Ctrl+g w / `:ParleyToggleWebSearch` persists the choice, but does not force every answer to search. Anthropic uses server tools, Google AI grounding, OpenAI a configured search model, and CLIProxyAPI family strategies (Claude Anthropic route, Gemini normally none). Unsupported enabling reports an error. 🌎 means supported/enabled; 🌎? enabled/unsupported; absent badge means off, in picker/header/lualine. Sources: `atlas/context/web_search`, `atlas/providers/agents`, `atlas/providers/cliproxy-managed`. Minor gap: concrete supported model names are intentionally not promised; OpenAI search-model setup requires provider docs. Global default-on wording must not be paraphrased as universal model support.

13. **Recover failed login/setup without losing chats — login answerable, bootstrap recovery incomplete.** Use `:ParleyProxy status`, distinguish auth from quota/model errors, retry `connect`/`login PROVIDER` when appropriate, inspect the login window with d, reopen/copy its URL with o/y; Esc hides without canceling, c cancels. Authentication-recovery login does not resume the failed question: resend after success. First-use onboarding can resume its pending action after model selection, so these are distinct paths. `:checkhealth parley` and `:ParleyInspectLog` help diagnostics. Brew package removal preserves chats/shared logins; existing settings are preserved on upgrade. Sources: `atlas/providers/cliproxy-managed`, `atlas/infra/starter`, `atlas/infra/packaging`, `atlas/infra/logging`. Gap: interrupted initializer ownership requires explicit repair after closing instances, but no repair commands or safe exact paths are in the tool catalog. Those instructions are only linked to non-catalog packaging guides. Do not invent reset/deletion commands or recommend deleting the profile to repair login. The starter sentence “Uninstall ... removing those roots” is not clearly distinguished from Homebrew removal, whose chat-preservation guarantee is explicit elsewhere.

14. **Move/delete one chat versus whole tree — deletion answerable, move partial.** `:ParleyChatDelete` / Ctrl+g d deletes only the current file plus assets, not children; Finder Ctrl+d does likewise. `:ParleyChatDeleteTree` / Finder Ctrl+g D walks to the root and deletes all descendants, including the current child's parents and siblings. Confirmation defaults No; no trash/undelete exists. `:ParleyChatMove` / Finder Ctrl+x moves a tree to another registered root and rewrites links; assets move with chats. Sources: `atlas/chat/lifecycle`, `atlas/ui/pickers`, `atlas/chat/attachments`. Gap: no user-facing command/procedure for moving exactly one chat is documented, although attachment internals mention `move_chat`. Move wording says “root + descendants” without explicitly saying whether invocation on a child includes ancestors/siblings as tree deletion does. Single deletion's effect on surviving parent/child links is not documented; do not claim automatic link cleanup.

15. **Default file-tool directory and roots in project versus profile — answerable except history-search inconsistency.** Relative tool paths resolve against the owning project root for repo chats, otherwise the chat's directory, never against each extra read root in turn. Default read/write access is that primary root; `tool_read_roots = {}` adds nothing. Extra absolute/relative roots grant reads only, relative extras resolve from the primary root, and symlink realpaths must remain allowed. Project chat nesting does not move the base. Finder discovery may include global/peer chats without granting equivalent tool access. Sources: `tutorials/advanced`, `atlas/infra/starter`, `atlas/infra/repo_mode`, `atlas/providers/tool_use`, `atlas/modes/super_repo`. Contradiction: `atlas/providers/tool_use` explicitly calls pathless `chat_history_search` unaffected by root-policy scope and says it searches ALL roots; starter says trusted per-request policy filters it and model input cannot widen it. This must be resolved before an unqualified cross-root privacy/scope claim.

16. **Can parley_help query tutorials and personal files? — answerable.** Tutorials yes: `tutorials/welcome`, `tutorials/basics`, `tutorials/advanced`; no topic lists IDs, and `README` or an atlas ID reads installed documentation. Personal files and source code are outside this tool; general file tools separately enforce allowed roots. Explicit agent tool lists can omit help, and direct Google AI lacks the client tool wire. Sources: `atlas/infra/starter`, `atlas/index`, `atlas/providers/agents`, `atlas/providers/tool_use`. Gaps: the main Tool Set table does not list `parley_help`, so discovery depends on the index/starter topic. `parley_help = false` explicitly disables injected introductory context, but whether it also removes the tool is not stated clearly; avoid claiming both. README links to packaging guides/contributor files and index links traceability YAML that help cannot retrieve as topics; accessible local links do not imply callable help topics.
